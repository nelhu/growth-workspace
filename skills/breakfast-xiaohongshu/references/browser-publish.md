# Chrome 图文发布流程

仅在用户明确要求“发布”或“生成并发布”时读取并执行本流程。仅生成、预览、修改 Skill 或已有每日定时任务不构成发布授权；升级 Skill 不会把旧定时任务改成自动公开发布。明确授权已覆盖目标内容包时，可完成最后提交，无须在每个常规步骤重复询问。

## 已验证经验与适用边界

- 优先使用用户本地 Chrome 的 Computer Use，复用登录态和同一浏览器会话。入口为 `https://creator.xiaohongshu.com/publish/publish`，选择第二个 Tab“上传图文”。不使用 `xiaohongshu-mcp`、`publish_content` 或 `breakfast_xhs.py publish`。
- 本会话中，逐张上传、输入标题正文、提交后检查“发布成功”页面的流程已成功使用。成功页路径是 `/publish/success`；动态查询参数不是固定定位条件。
- 中文逐字输入曾出现缺字，优先对可编辑文本字段使用当前工具支持的 `setValue`。`paste` 曾出现旧剪贴板内容，不能把粘贴调用成功当作正文正确：每次读回全文，发现错贴即清除该字段并重新输入。
- 正文曾通过先写完整文本、再从后向前定位段首并插入换行完成排版。当前编辑器若正确保留多行文本，可直接输入，但仍须读回验证。
- 之前没有完成置顶评论发布；不得把正文提交成功描述为置顶评论已发布。话题出现 `#文本` 也不证明已绑定为平台话题。
- 下列等待、分段及重试参数是用于可靠性的新默认值，不是已证明能够避免风控的参数。不得承诺“不被识别人机”，不使用随机点击、伪造人工行为、指纹伪装或其他规避平台检测措施。

## 浏览器可靠性与平台合规策略

目标是减少动态页面、网络延迟和编辑器识别造成的误操作，不是伪装真人或绕过平台风控。实现依据采用浏览器自动化的通用可靠性原则：优先使用面向用户的 role/label/text 定位；动作前确认目标唯一、可见、稳定、可接收事件、已启用，文本字段还需可编辑；用页面状态和回读断言决定是否继续。参考 [Playwright Auto-waiting](https://playwright.dev/docs/actionability)、[Playwright Locators](https://playwright.dev/docs/locators) 与 [Selenium Waiting Strategies](https://www.selenium.dev/documentation/webdriver/waits/)。

发布模式必须执行以下规则：

1. 每次动作都基于最新 AX/截图重新定位，优先 role、label、placeholder、可见文本等用户可感知属性；不用旧坐标、脆弱 DOM 层级或隐藏元素。
2. 点击前在最多 15 秒内确认元素唯一、可见、稳定、未被遮挡且已启用；输入前额外确认可编辑。条件不满足时不强制点击。
3. 等待必须由可观察状态结束，例如缩略图数量增加、字段值回读一致、候选列表出现、话题转为原生实体或 URL 进入成功页。固定间隔只用于短轮询，不用长睡眠替代状态判断。
4. 标题和正文优先一次写入可验证字段；正文需要分段时按语义边界处理。只有话题候选必须依赖逐键触发时，才对当前单个话题使用约 40–80 ms/字符的顺序输入，并在候选出现后立即停止；这个节奏用于确保输入事件被编辑器处理，不用于拟人。
5. 页面发生上传、候选选择、弹层开关或路由变化后，以 0.5–1 秒间隔检查目标状态，最多等待 15 秒；单张图片上传最多等待 60 秒。状态满足立即继续，不额外随机等待。
6. 可逆动作仅在回读确认“未生效”后重试，最多 2 次，退避约 1 秒、3 秒；重试前刷新 AX/截图。字段已部分生效、结果不明或可能产生重复内容时停止自动重试。
7. 不移动鼠标制造轨迹，不点击无关区域，不随机改变打字速度，不修改浏览器指纹/User-Agent，不隐藏自动化特征，不处理验证码。遇到验证码、风险提示、账号限制或平台强制声明立即暂停并交给用户。
8. 最终“发布”每次授权只点击一次；点击前先写 `publication.json.status=unknown`，点击后仅通过成功页或笔记管理实际记录确认结果。

## 参数速查

| 项目 | 默认值与判断依据 |
| --- | --- |
| 动作可交互等待 | 最多 15 秒；唯一、可见、稳定、可接收事件、已启用，输入框还需可编辑 |
| 状态轮询 | 每 0.5–1 秒检查可观察状态；完成条件满足即继续，不靠固定长睡眠猜测完成 |
| 输入分段 | 正文较长时每段约 50–100 字，按语义边界拆分；不强制逐字模拟打字 |
| 话题顺序输入 | 仅在候选依赖逐键事件时使用约 40–80 ms/字符；每次只输入一个话题并等待精确候选 |
| 输入确认 | 每次字段写入或段落插入后读回，检查中文、标点、换行及有无重复 |
| 上传等待 | 每张图最多观察 60 秒，确认上传完成且缩略图可见后再继续 |
| 普通动作重试 | 仅对可逆且已确认未生效的动作最多重试 2 次；约 1 秒、3 秒退避，先更新 AX/截图 |
| 最终提交 | 每次授权执行只点击一次“发布”；超时、断网或未知返回不能自动再次提交 |

不要把等待超过一分钟的单次阻塞调用作为轮询。遇到验证码、风险提示、账号限制或人机验证，立即暂停并交给用户处理；不代做验证码，不调整模拟参数尝试绕过。

## 发布前核验与重复提交保护

1. 明确目标日期、内容包及账号。读取目标目录的 `README.md`、`content-package.json` 和已有 `publication.json`，运行 `validate-manifest`；失败先修复，不能边发布边补齐。
2. 如已有 `publication.json.status=published`，不得重复提交。若为 `unknown`，先只读检查创作中心笔记管理；以标题、封面、时间等核对是否已创建。仍无法确定则暂停，不能把再次运行视为重试发布的授权。
3. 核对至少 3 张 `853×1280 px` 图片及顺序：家庭餐桌首图、总览信息图、菜品过程图。标题不超过 20 字符，使用当前早餐吸引力标题规则，不擅自恢复天数或栏目名前缀。
4. 正文不添加“配图为 AI 辅助搭配示意”等声明。按内容包准备正文、互动问题、明天预告和 10 个话题；置顶评论另行处理。核对话题与当日台账一致，不在编辑器中临时换为猜测的热词。
5. 浏览器只操作目标账号和目标笔记，不修改其他打开的页面。若已有发布草稿，不覆盖不明草稿；先核对是否属于本次内容包。

## 网页操作

每个动作批次后获取新的 AX 状态或截图，再决定下一步。元素编号及坐标只使用当前状态，不复用旧会话坐标；缺少 AX 元素时再依据当前截图点击。

1. 打开入口并选择“上传图文”。未登录则让用户完成需要其交互的登录；不搜索或导出账号凭据。
2. **逐张上传**：触发上传按钮，在系统文件选择器使用 `Command+Shift+G` 进入目标绝对路径，确认选中文件再点“打开”。每张上传后等待完成，读回图片数量和缩略图顺序；重试前检查是否已经成功，避免重复图。
3. **标题**：写入内容包标题并读回，检查平台字数反馈。若平台限制与本地计数不同，先调整为等义短标题并在交付记录中保留最终使用的标题。
4. **正文**：依次写正文、互动问题、明天预告，段落间保留空行。优先 `setValue`，不可用时采用可读回的输入方法；不要把剪贴板内容未经核对直接提交。需逐段修复换行时，从后向前定位段首再插入换行，避免前面编辑改变后续位置。
5. **话题逐个绑定（硬规则）**：按台账顺序，每次只处理一个话题，完成下列闭环后才输入下一个；禁止一次粘贴整组话题，也不能用 `setValue` 重写整个正文来追加话题。
   - 将光标放到正文末尾的话题区域，输入当前单个 `#话题名`，或通过“话题”按钮输入该名称。
   - 等待当前话题的候选/识别反馈，出现候选列表时选择名称完全匹配的条目；不得无条件按 Enter、点击首条或改选近似话题。
   - 获取新的 AX/截图，确认刚输入的名称已转为编辑器原生话题样式（用户样例中的蓝色话题文本），结合候选选择结果或可见话题实体反馈核验；不能靠手工变蓝、普通 `#文字` 或输入成功返回值代替识别。
   - 确认当前话题完整且未重复，前面已绑定的话题仍保留，然后退出当前话题输入状态、移到其后，再添加下一个。不要提前批量输入后统一检查。
   - 最后按台账逐项核对 10 个名称、顺序和识别状态，保留最终截图/AX证据。任一话题未识别、候选没有精确匹配或绑定状态不明时，记录该项为 `plain_text_only` 或 `unknown` 并暂停发布，不擅自换词或带着未绑定话题提交。
6. **声明与其他设置**：按 Tiny.C 当前偏好，不主动选择“笔记含 AI 合成内容”或“含 AI 生成内容”。若平台自动添加或强制要求则保留并告知，不能移除强制标识或绕过要求；个人账号声明不是平台豁免证明。原创声明中的协议或承诺不能仅因内容包 `is_original=true` 而自动同意。无关定位等权限不主动开启。
7. **最后核对**：获取新 AX/截图，检查实际账号、图片数量与顺序、最终标题、完整正文、10 个已识别话题、可见范围及声明状态。点击之前先写入 `publication.json`，标记 `status=unknown`、`submission_attempted_at` 为当前时间，说明“即将提交，结果待核实”；即使进程中断，下次也必须先查笔记管理。保存核验结果后，仅点击一次“发布”。
8. **结果核验**：看到明确“发布成功”并处于成功页，或在笔记管理找到本条对应笔记，才能写为 `published`。仅有按钮点击返回、页面跳转、加载结束或泛化提示不构成成功证据。提交后无明确结果则写 `unknown`，保存当前页面证据并停止重复提交；提交前被验证码、校验或账号问题拦截则写 `blocked`。

## 独立发布记录与交付同步

话题识别视觉参考：[用户提供的蓝色话题样例](../../../assets/xiaohongshu-topic-recognition.png)。它仅说明预期效果，不作为当前表单已绑定成功的证据；每次仍须现场逐个核验。

在当日内容目录中维护 `publication.json`。它用于记录网页发布事实，不是改变 `content-package.json` 生成策略的开关：保留生成包的 `status=ready_for_review`、`should_publish=false`，不要通过篡改这些字段绕过生成校验。

记录至少包含：

```json
{
  "date": "YYYY-MM-DD",
  "status": "published | unknown | blocked",
  "channel": "chrome_computer_use",
  "account": "页面实际核对的账号",
  "published_title": "实际使用的标题",
  "visibility": "页面实际核对的可见范围",
  "submitted_at": "含时区的实际时间；未提交时为 null",
  "verified_at": "含时区的实际核验时间",
  "result_url": "实际成功页或笔记链接；未获取为 null",
  "note_id": null,
  "evidence": "成功页明确文案或实际保存的页面证据路径",
  "topic_binding_status": "verified | plain_text_only | unknown",
  "topic_bindings": [{"tag": "#实际话题名称", "status": "verified | plain_text_only | unknown", "evidence": "本话题实际识别反馈"}],
  "ai_label_state": "实际观察值：未主动选择、平台自动添加或平台强制要求",
  "pinned_comment_status": "not_posted | posted | pinned | unknown",
  "failure_reason": null
}
```

以上是字段示意，写入时必须使用一个真实状态和实际值；`topic_bindings` 按台账顺序记录全部 10 项，只有全部 verified 才将汇总状态标为 verified。未知链接、笔记 ID 或证据不能编造。不要在记录中保存 Cookie、Token 或账号凭据。

- 同步 `README.md` 的发布状态、实际标题、时间、结果链接及发布记录链接，保留原内容包链接。成功页只证明发布提交成功，不等于平台审核通过或已获取公开笔记 ID。
- 确认 `published` 后，才运行 `python3 skills/breakfast-xiaohongshu/scripts/breakfast_xhs.py record /absolute/path/content-package.json --published`。执行前重新通过 manifest 校验；记录历史失败不改变已经发生的发布事实，应单独报告。实际可见范围以 `publication.json` 的网页核验记录为准。
- 用户明确要求发布并置顶评论时，进入已核对的目标笔记，单独提交内容包置顶评论并核验其出现，再操作置顶并确认成功；两个状态分别记录。仅要求发布帖子时，默认不附带发布评论。此前未执行成功的置顶步骤不得宣称为已验证经验。
- 按当前任务已有的 Git 授权范围提交/推送当日产物及发布记录；Git 失败与小红书已发布分别报告，不能因此重新发布。
- 最终如实报告目标日期、标题、发布状态和证据链接；置顶评论、审核状态、话题绑定及 Git 未闭环项分别说明。
